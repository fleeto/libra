## 文档职责

本计划解决 issue #497（commit 系列）：当删除仓库中**最后一个被跟踪文件**、并经 `libra rm <path>`（或 `libra add -A` / `commit -a`）**暂存**该删除后执行 `libra commit`，libra 误报 `nothing to commit, working tree clean`，而没有真正提交这次删除。Git 的行为是：删除最后一个被跟踪文件（清空 worktree 内容）后 `git rm <last-file> && git commit` / `git commit -a` / `git add -A && git commit` 应产生一个提交（树为空，相对于 HEAD 为一次删除），而不是 "nothing to commit"。**暂存是前置条件**：未暂存的纯文件系统删除不进入索引，plain `libra commit` 仍必须按 Git 拒绝（`no changes added to commit`，`LBR-REPO-003`）——本计划同样锁定该拒绝语义。

「文档职责」全文：目标是对齐 Git 的「删除最后一个被跟踪文件」语义——经暂存的该删除是**应落入索引与提交**的有效变更，而非空工作树；未暂存的删除仍是被拒绝的未暂存改动。

本文记录已完成的计划、实现结果与验收证据；源码锚点和证据均以 2026-09-28 收口时的 checkout 为准（2026-10-04 R3 收口增补的测试与文档锚点以当日 checkout 为准）。

### 适用范围

- `libra commit` / `commit -a` / `commit -am` 在"删除最后一个被跟踪文件"（经 `libra rm` / `add -A` 暂存）下的判定与输出。
- 索引 vs 工作树的"是否有变更"判定；删除（D）与 untracked 空目录的区分；未暂存删除的拒绝分型。
- 相关的 `status`/`ls-files` 输出一致性。
- 同步：commit 文档、`COMPATIBILITY.md`、`../libra-backend` 文档、compat 守卫。

### 非目标

- `add` 家族（#484/#489/#491–#494）的删除/未合并语义。
- 交互式 commit、`--amend` 空消息（#478）。
- 空树提交（`--allow-empty`）的独立行为。

### 成功定义

- 删除最后一个被跟踪文件并暂存（`libra rm <path>` 或 `libra add -A`）后，plain `libra commit`、`libra commit -a`、`libra add -A && libra commit` 三条路径均**成功**产生一个删除型提交（HEAD 树不再含该文件；仅 `rm` / `commit -a` 路径下 HEAD 树为空——`add -A` 会同时拾取 untracked 的 `.libraignore`，与 `git add -A` 语义一致）；`commit` 不再误报 `nothing to commit`。
- **未暂存**的纯文件系统删除（不经过 `libra rm` / `add -A` / `commit -a`）被 plain `libra commit` 拒绝：文案 `no changes added to commit (use "libra add" and/or "libra commit -a")`、错误码 `LBR-REPO-003`、退出码 `128`。
- 若工作树确实干净（无任何变更），`commit` 仍按 Git 报 `nothing to commit, working tree clean`；默认 `LBR-REPO-003` 退出码为 `128`（若启用 `LIBRA_FINE_EXIT_CODES=1`，则为 repo 类别码 `3`）。
- 暂存删除后 `status --porcelain` 报 `D  <path>`、`ls-files` 输出为空，与 Git 对拍一致。
- 移植对应的 Git 上游场景（删除最后一个被跟踪文件 → commit 成功），并有回归守卫。
- 任务卡取得 C 组发布与 D 组证据，收口门全绿后才标记完成。

## 已决议设计决策

### ADR-CD-01: 空索引 + 相对 HEAD 存在暂存删除时允许提交

- **Status:** Accepted
- **Context:** 删除仓库中最后一个被跟踪文件后（`libra rm <path>` 或 `libra add -A`），索引变空。`commit -a` 时 `auto_stage_tracked_changes` 因索引已无被跟踪文件而找不到工作树变更，返回 `false`（`auto_stage_applied=false`）；随后 `src/command/commit.rs` 的 `tracked_entries.is_empty() && !allow_empty && !is_amend && !auto_stage_applied` 门被触发，误返回 `NothingToCommitNoTracked`（`nothing to commit (create/copy files and use 'libra add' to track)`，`LBR-REPO-003`）。Git 的 `git rm <last-file> && git commit` 会真正产生删除提交，而 `libra commit` 误报"无变更"。
- **Decision:** 先计算 `status::changes_to_be_committed_safe()`（相对 `HEAD` 的暂存变更），再把「空索引即无变更」的门收紧为 **`tracked_entries.is_empty() && staged_changes.is_empty()`**。这样：
  - 删除最后一个被跟踪文件（索引空，但相对 `HEAD` 存在 `deleted` 变更）→ 条件为假 → 正常走提交，产生删除提交。
  - 真正空仓库（无任何提交、未暂存任何文件）→ 相对 `HEAD` 无可提交变更 → 仍返回 `NothingToCommitNoTracked`，文案与 Git 一致。
  - 干净工作树（相对 `HEAD` 无变更）→ 仍由 `classify_nothing_to_commit` 分型（`nothing to commit, working tree clean` / `nothing added to commit but untracked files present` / `no changes added to commit`）。
- **Alternatives considered:** (1) 移除 `tracked_entries.is_empty()` 门，完全依赖 `staged_changes.is_empty()`——但这样空仓库无文件时会把"从未暂存"误报为 `nothing to commit, working tree clean`，丢失 Git 的 `create/copy files` 专属文案，故不采纳。(2) 让 `auto_stage_tracked_changes` 在索引为空时仍返回 `true`——不准确（该函数语义是"是否找到工作树可暂存变更"），且不解决 `add -A && commit`（无 `-a`）路径。(3) 在 `libra rm` / `add -A` 删除最后文件时保留一个空 tree 以规避"空索引"——不必要，索引本身变空是正确语义。
- **Consequences:** `commit` / `commit -a` 的判定顺序发生变化（先算相对 `HEAD` 暂存变更再分类）。**成本口径（2026-10-04 修正）：** `changes_to_be_committed_safe()` 并非纯内存读——它从磁盘加载索引（`Index::load`）、解析 `HEAD`、从对象库读取 HEAD commit 与 tree 对象，并遍历 tree 条目与索引逐项比对（`src/command/status.rs:980-1036`；`content_changed` 走 `index.verify_hash` 的哈希比对），复杂度 O(索引条目 + HEAD tree 条目) 的对象读取，**不做工作树目录扫描**。在提交成功路径上该计算原本就会执行（构建提交需要相对 HEAD 的变更集），本决策只是把它提前到空索引门之前，属于既有计算的重排序；仅「无可提交变更」的拒绝路径相比原先的提前返回多出一次 HEAD commit/tree 读取与同量级遍历，无无界扫描，符合 GC-10。`status --porcelain` / `ls-files` 输出不受影响（保持与 Git 一致：`D  <path>` / 空）。
- **Revisit when:** 若 `changes_to_be_committed_safe` 的未来实现改变"相对 HEAD 变更"的定义，或 `add`/`rm` 的索引语义调整，应重审本判定的排序与 `NothingToCommitNoTracked` 文案。
